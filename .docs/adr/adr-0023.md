# ADR-0023 — Runner control-plane API

## Context

WP-01 defines a private runner service that creates and destroys ephemeral sandboxes. The technical specification §16.3 requires a narrow, audited API surface for sandbox control, but it does not fix the request and response shapes. WP-13 (orchestration) must call the runner and WP-14 (sandbox runner) must implement it without drifting. Without a recorded contract, the two WPs would invent incompatible interfaces and the worker could be tempted to call the Docker Engine directly.

## Decision

Adopt the runner control-plane contract in `docs/contracts.md` §2 as the v1 interface:

- Private HTTP on the `runner` network, authenticated by `AILAB_RUNNER_TOKEN` (≥ 32 bytes), bound to the internal interface only.
- Endpoints: create sandbox, status, log stream (SSE), allowlisted exec, delete, health.
- Creation is idempotent by `run_id`; the runner never mounts the Docker socket into a sandbox; every call is logged with `run_id` and `trace_id`.
- The contract is versioned by path (`/v1`). A breaking change requires `/v2` and a coordinated rollout.
- WP-13 is the only consumer; WP-14 is the only implementation. A contract-compatibility test is required before either WP closes.

## Consequences

- The worker never talks to the Docker Engine directly; the blast radius of a sandbox bug is confined to the runner.
- The contract test becomes a release dependency for WP-13 and WP-14.
- The token and network isolation add deployment configuration that WP-03 must provision.
- The SSE log stream and the exec allowlist must be implemented carefully to avoid command injection and log flooding.

## Alternatives considered

1. Let the worker call the Docker API directly. Rejected: broad privileges, no single audit point, higher escape blast radius.
2. Use gRPC between worker and runner. Rejected: an extra dependency and codegen burden for a single internal consumer; HTTP/SSE is sufficient and easier to test.
3. Run sandboxes in-process with `bollard`. Rejected: no process isolation, harder crash recovery, and no separate resource boundary.
4. Leave the contract to WP-14. Rejected: WP-13 cannot be built against an undefined interface; drift is inevitable.

## Status

Accepted on 2026-11-07 by Tech Lead, Dev and QA.
