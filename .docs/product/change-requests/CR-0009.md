## context

The review of WP-00..WP-12 found and fixed real defects. The review of WP-13 and a spot check of WP-14 show a structural pattern: the WPs are marked `done`, but their contracts require a running platform that the repository does not contain.

- WP-13: only the scheduler/lease/state/retry/budget subset exists; the 13-stage pipeline, context builder, agent loop, verification runner, PR/handoff, run APIs/events and E2E are missing. A domain state machine was added on `review/wp-13-orchestration-impl` (28 tests) but the QA returned `CHANGES_REQUESTED`.
- WP-14: `sandbox.rs` provides policy types, but the runner is a health-only placeholder; the HTTP control-plane API, exec/logs, live escape suite, egress proxy wiring and token injection are deferred to a "follow-up" while the contract lists them in scope.

Continuing to mark these WPs `done` is a false gate under the Constitution. The remaining WPs (15–23) depend on them.

## proposed_change

1. Keep WP-13 in `progress`; keep `review/wp-13-orchestration-impl` as an increment, not a completion.
2. Reopen WP-14 from `done` to `progress` and require the runner HTTP API, exec/logs, isolation/escape suite and egress runtime.
3. Record the review plans for WP-13 and WP-14 with the exact gaps.
4. Sequence the remaining work as a **build phase**: WP-14 runner → WP-16 API/realtime → WP-13 integration → WP-15 QA/merge → WP-17..WP-19 UI → WP-20/WP-21 ops/testing → WP-22/WP-23 release/maintenance.
5. Do not close any of these WPs until its blocking acceptance criteria are verified.

## impact_scope

- `.docs/sow/SOW.md` index statuses
- `.docs/sow/WP-14-SANDBOX-RUNNER.md` status/history
- WP-13/WP-14 review plans
- The build sequence for WP-15..WP-23

## impact_schedule

WP-14 and WP-16 are on the critical path for WP-13; M5 moves behind the build phase.

## impact_cost

Substantial: postgres leases + worker loop, axum run APIs, sandbox runner backend, adapter wiring, E2E/chaos.

## impact_risk

The baseline cannot be declared complete; the alternative is to keep shipping false `done` statuses, which the review exists to prevent.

## alternatives

1. Mark WP-13/WP-14 `done` with deferrals. Rejected: the contracts list the deferred items as in-scope and the QA rejects them.
2. Build everything in one pass without re-baselining. Rejected: it hides the schedule impact and the dependency order.

## decision

`approved`. Reopen WP-14, keep WP-13 in progress, and run the build phase in the stated order.
