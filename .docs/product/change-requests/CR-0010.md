## context

WP-16 is marked `done`, but its own deliverable checklist defers the axum router, DTO generation, full middleware ordering, Redis idempotency store, WS hub/backpressure, outbox fan-out, Swagger UI and HTTP health endpoints. Those items are in scope per §2.1/§3.1–§3.12. A first build increment (health, run endpoints, Problem Details, rate limiter, WS hello/subscribe) is now implemented in `crates/api/src/server.rs`; the remaining contract is still open.

## proposed_change

Reopen WP-16 from `done` to `progress`, record the increment and the remaining gaps in a review plan, and keep the WP open until the full edge contract is delivered and QA-approved.

## impact_scope

- `.docs/sow/WP-16-API-REALTIME.md` status/history
- `.docs/sow/SOW.md` index
- `.docs/sow/WP-16-API-REALTIME-review-plan.md`
- `crates/api`

## impact_schedule

WP-17..WP-20 consume the API; their verification waits for the full edge contract.

## impact_cost

DTOs, idempotency store, WS hub/backpressure, outbox fan-out, telemetry ingest, Swagger UI, contract/perf tests.

## impact_risk

Closing WP-16 on contract-only artifacts is a false gate; the QA review exists to prevent it.

## alternatives

1. Keep WP-16 `done` with deferrals. Rejected: the contract lists the router/WS in scope.
2. Build the full edge in one pass. Rejected: it hides the schedule and dependency impact.

## decision

`approved`. Reopen WP-16 and deliver the edge server incrementally.
